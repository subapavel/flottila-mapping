# The mapping-model schema is the source: generated TS types, hand-written Java records, three-stage validation

Status: accepted (2026-10-30, grilling #6); amended by F-2

FOUNDING §12 says the editor's model types are generated from the mapping-model schema. This
ADR records that and fills the gaps for the Java side and for validation.

- `mapping-model.schema.json` is JSON Schema draft 2020-12 with `$id`
  `urn:flottila:mapping-model:<formatVersion>`. It is the source of the format. It closes every
  object with `additionalProperties: false`, uses `oneOf` with a `const` `kind` for box kinds,
  and never uses `prefixItems` or `unevaluatedProperties`.
- The editor's TypeScript types are generated by json-schema-to-typescript 16 (MIT) and
  committed. CI regenerates them, and the diff must be empty.
- The Java records of the mapping front end are hand-written: a sealed `Box` and one record per
  kind. A test compares the schema's properties with the record components.
- `function-catalogue.json` follows the same canonical-form rules (ADR-0010) and has its own
  schema. It is keyed by function name. Each entry holds `poName`, `cpiName`, `executionKind`,
  the inputs with their `poPin`, the parameters with type and default, `portable`,
  `deterministic`, `fidelity` (level, deviation id, example, ambiguity) and `patternLetters`.

## Validation

There are three stages. Each error carries the `AuthoringId` of the element it concerns, where
there is one.

1. **Schema**: json-sKema 0.32.0 validates the file. It checks shape, kinds, id patterns and
   unknown members, and fails closed. A failure names the JSON pointer of the instance.
2. **Model check, on load**: it checks that ids are unique, that references resolve inside
   their target field mapping, that the graph is acyclic, and that a context is a proper
   ancestor of its field. The check works on the path text.
3. **Compile**: everything that needs the structure, the catalogue or the UDF sources raises a
   design-time error (ADR-0006):
   - an orphaned reference;
   - an unknown function, a wrong arity, or a parameter that cannot be cast;
   - a pattern that does not translate;
   - an unresolved box;
   - an unconnected input, or an unconnected target field (`result` is `null`, F-2);
   - a UDF that does not match its declaration;
   - a fingerprint mismatch.

## Considered options

- **quicktype 26** for the TS types: rejected. It merges a `oneOf` into one interface and so
  loses the discriminated union (observed).
- **jsonschema2pojo 1.3.3** for Java: rejected. It emits no records and does not support
  2020-12 (observed in the jar).
- **Our own record generator**: deferred. It is not worth it until the model grows past a few
  dozen types.
- **Records first, schema generated**: rejected. FOUNDING §12 makes the schema the source, and
  Java refactors would change the format.
- **A second validator library for the model**: rejected. json-sKema is already in the stack.
  F-1 amends ADR-0008 to allow it.

## Consequences

- The drift tests are mandatory: generated TS up to date, schema properties = record
  components, and no `prefixItems` or `unevaluatedProperties` in the schema.
- Facts behind this ADR were observed on 2026-10-30 in a scratch directory and not committed:
  - json-sKema 0.32.0 validates 2020-12 instances on JDK 25, with `$defs`, `oneOf` + `const` and
    `additionalProperties: false`;
  - json-schema-to-typescript 16.0.0 turns `oneOf` + `const` into a discriminated union and drops
    `prefixItems` and `unevaluatedProperties`;
  - Jackson 2.20 and 3.2 bind records.
