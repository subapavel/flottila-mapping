# F-22 — A single-value `if` short-circuited in the runtime but not in the export

- **Assumption** (#77, ADR-0006 single-value calls): `if` over single values behaves the same in the runtime and the export; nothing said whether its untaken branch is evaluated.
- **How it fails**: `BooleanFamily.ifValue` evaluated only the taken branch. Saxon-HE 12.5 evaluates the `$else` argument of `po:if` eagerly. In `if(Sku, Qty, divide(1, 0))` with every Sku `true` the runtime wrote the output and the export raised division by zero. Over a queue branch (`divide(Qty, 0)`) both back ends already evaluated every box and both raised.
- **Severity**: major (the back ends disagree on whether a mapping fails)
- **Evidence**: spec-3 review R3, `.logs/70r-r3.log` and `.logs/70r-r3-probe.log` on `t/70-review`, test `UntakenBranchDataErrorTest` (engine/oracle).
- **Change made**: every input of a single-value call is evaluated before the call, as PO computes every input queue of a box before the box runs. `ifValue` evaluates both branches; a data error in the untaken one is raised at its box in both back ends. ADR-0006 amended. An export that relied on a lazy processor for this would be F-18's problem; this rule needs none.
