# F-15 — ADR-0025 puts every function into files that every function ticket edits

- **Assumption** (CODING_STANDARDS, Module boundaries): "No central registry file that every ticket
  edits … Families register themselves (one file per family, ServiceLoader or generated index)".
- **How it fails**: ADR-0025 (accepted for #50) gives each new function one entry in
  `function-catalogue.json`, one case in the `QueueLibrary` binding switch, one `ContextFunctions`
  method and one `po:` function in `po-runtime.xsl`. `ContextFunctions` and the binding switch are
  files of one family (context functions) and pass the rule; the catalogue and `po-runtime.xsl`
  hold every family and are central registries. ADR-0025 never weighed the rule.
- **Severity**: non-blocking for spec 2; blocking for spec 3.
  - Spec 2 adds only context functions, at most three writers at once. Their edits are appends at
    one place in each file, which the merger resolves as mechanical adjacent edits (AGENTS.md).
  - Spec 3 adds many families in parallel; there the conflicts would be the rule, not the exception.
- **Evidence**: #50 implementer hand-back (self-check 5); #50 standards review (2026-11-02), which
  rated it a finding, not a violation of #50.
- **Change made**:
  - Spec 2 keeps ADR-0025 as is. The merger treats a conflict in these four files as mechanical
    when both sides only add whole entries.
  - Before spec 3's function tickets start, a prefactor ticket splits the catalogue into one
    canonical file per family and `po-runtime.xsl` into one included module per family
    (ADR-0023 still ships one entry module). ADR-0025's Consequences note this.
  - #51 adds `SingleValueLibrary`, the binding switch for single-value functions. It is keyed by
    execution kind, not family, so spec 3's text, arithmetic, date and boolean functions would all
    land in it: the same prefactor splits it per family (#51 standards review).
