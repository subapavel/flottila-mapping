# F-46 — `copyValue` selects across the whole queue and yields a generating value

Status: open (#217, 2026-11-13). The observed rule is clear and PO 7.5 and CPI agree, but it is
not a queue function: its result is a generating value, which today only a graph without a source
field can give (ADR-0006 "generating function", since #83). `fn/copyValue/001`–`004` are corrected
to the observed outputs and are red. The code, ADR-0006 and the fidelity stay as they are until the
architect scopes the change below.

- **Assumption** (assumed reading of #79, in `ConstantFunctions.copyValue` and `po:copyValue`; no
  ADR line, ADR-0025 l.59 lists the id only): per context of the input, one context holding the slot
  at the position, counted from 0; a context too short gives an empty context; a SUPPRESS slot is
  copied as SUPPRESS.
- **How it fails**: observed the same on PO 7.50 and CPI (obs-constant, 2026-11-12/13):
  - The position counts from 0 across the whole input queue, context boundaries ignored. Sku in
    context Order is a, b, c | d | e, f: Index 1 selects b, the default Index 0 selects a, Index 3
    selects d (CPI: "selects d across the entire input queue, ignoring context boundaries").
  - That one value goes into every parent occurrence: V b, a, d in all three Items, also in o2's,
    whose context has no such position.
  - A SUPPRESS slot counts as a position and is copied: over `createIf(Tag)`, "", SUPPRESS, "" |
    SUPPRESS, "" | (empty), Index 1 selects SUPPRESS and no Item gets a V.
  - F1's display queue holds one value, with the shape of a `Constant`'s output (PO: `[b]` gray,
    `[b]` dark gray, as C1 in `constant-003`; CPI: "output generator b followed by end marker"),
    not one context per input context. `count` of a constant shows a context and gives V in the
    first Item only (`constant-006`), so the repeat is the generator's, not the target's.
  - The editor proposes Index 0 on both; PO refuses an empty Index, CPI saves it as 0.
  - Not observed: a position beyond the last slot of the queue, an empty queue, and `copyValue`'s
    result at a single-value or context function's input.
- **Severity**: major. Every Item but the matching one differs, and where PO copies SUPPRESS into
  every Item we write an empty V (`fn/copyValue/004`, o2).
- **Evidence**: `corpus/observations/obs-constant/{po75,cpi}/copyValue-00{1,2,3,4}-*.xml` and
  `-check.txt`, `cpi/copyValue-00{1,3,4}-F1-queue.json`, `cpi/copyValue-004-C1-queue.json`,
  `cpi/native-default-copyValue-002.txt`, `po75/constant-003-constant-item-check.txt`,
  `po75/constant-006-constant-count-check.txt`, `meta.json`; #212 comment "Observation run vs
  assumed corpus cases", group G5; red run `.logs/217-oracle-red.log` of `t/217-copyvalue`.
- **Change made** (proposed, not yet made): the rule does not fit #217's paths
  (`engine/runtime`, `engine/xdm`, `constant.xsl`). A queue result is read by `TargetSlots` per
  parent context (`po:slots`), and only `Lowering` (engine/mapping) makes a target a generating
  `TargetRepeat`, from a result that is a single `STRING` value, which cannot be SUPPRESS. The
  observed rule needs: a box with a queue input whose result is a single value (lowering and IR
  typing, ADR-0006 "Functions by execution kind"); a generating value that may be SUPPRESS, which
  creates no copy (`TargetRepeat` in the interpreter and the export's code generator); and that
  value at a `Lift` or context input as for `constant` (`AtomicToQueue`). Then ADR-0006 Consequences
  states the rule, citing this finding, `copyValue` becomes `exact`, and `fn/copyValue/001`–`004` go
  green on both back ends. Emulating it with one context per input context gives the four outputs
  but contradicts the display queues, and differs when the input's context is not the parent's.
