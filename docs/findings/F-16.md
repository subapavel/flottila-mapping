# F-16 — The mutation ratchet counts timed-out mutants as killed, so a score depends on load

- **Assumption** (ADR-0019, ADR-0017 ratchet): a module's mutation score is a property of its
  code and tests, so the ratchet can only fall when a ticket weakens them.
- **How it fails**: PIT counts a `TIMED_OUT` mutant as killed. Whether a mutant times out
  depends on the machine's load (no timeout is configured, so PIT's defaults apply).
  - After #59 the verifier's spec gate counted three `engine/mapping` mutants as timed out, and
    the ratchet rose to 97 %. In the #51 implementer's run they finished and survived, which
    put the module below its floor until extra tests killed them.
  - The #51 ticket gate shows `TIMED_OUT` 2 in `engine/xdm` and 1 in `engine/mapping`; without
    that one, mapping is 96.8 %, just above the floor by rounding.
- **Severity**: non-blocking. It can fail a later ticket for a mutant it did not touch, or let
  a ratchet rise that the next run cannot hold.
- **Evidence**: `.logs/48-pit.log` after #59 (verifier); `.logs/51-pit.log` in the verify-51
  worktree; the #51 implementer hand-back.
- **Change made**: none yet. Proposal for spec 5 (speed, with F-13): set PIT's `timeoutConstant`
  and `timeoutFactor` explicitly, and have `scripts/ratchet.java` compute the score with timed-out
  mutants counted as survived, or report them separately so a rise needs a run without them.
  Until then a ratchet drop that comes from timed-out mutants alone is judged by the architect,
  not treated as a ticket failure.
